TALID — خطة التنفيذ والتشغيل الشاملة

الإصدار: Release v1 — خطة التوافق والتجهيز والاختبار

1. الهدف من المنصة

TALID منصة تجارة إلكترونية ذكية لإدارة ومتابعة نشاط البيع في الأسواق العربية، مع الاستفادة من خدمات Taager وEasyOrders، وفق الإمكانات والصلاحيات المتاحة فعليًا في حساب المستخدم.

الأسواق المستهدفة:

- مصر
- السعودية
- الإمارات
- عُمان
- العراق

الهدف هو توحيد إدارة المنتجات والطلبات والأسواق والأرباح والتسويق والتكاملات في لوحة واحدة.

3. أعمال يجب استكمالها قبل الاختبار

أ. توافق قاعدة البيانات

يجب مراجعة التوافق بين:

- الجداول الأساسية القديمة.
- جداول التحكم التي أُنشئت لاحقًا.
- واجهة "web/app.js".
- وظيفة "talid-control".
- وظيفة "easyorders-webhook".
- وظيفة "talid-worker".

يجب التحقق خصوصًا من:

- اختلاف أسماء أعمدة الأسواق.
- الجداول التي تتوقعها الواجهة مثل "talid_products" و"talid_orders" و"talid_campaigns".
- اختلاف حالات المهام بين "pending" و"queued".
- أعمدة استقبال أحداث Webhook.
- قيود التكرار والمفاتيح الخارجية.

لا يتم إعادة تشغيل migration قديم أو إنشاء جداول مكررة دون مراجعة.

ب. إعداد الواجهة

- إنشاء "web/config.js" محليًا باستخدام Supabase URL وanon key.
- عدم وضع service_role key في المتصفح.
- مراجعة تسجيل الدخول والجلسة والصلاحيات.
- التأكد من أن كل أقسام الواجهة تتعامل مع الجداول الفعلية.

ج. وظائف Supabase

- مراجعة كود الوظائف الثلاث.
- ضبط أسرار التشغيل من إعدادات Supabase.
- اختبار المصادقة والتوثيق.
- اختبار استقبال الأحداث المكررة.
- التأكد من تسجيل الأخطاء.
- عدم تشغيل أي وظيفة تجارية قبل اجتياز الاختبارات.

4. مراحل التنفيذ

1. استكمال ملفات GitHub: مراجعة جميع ملفات الحزمة ورفع الناقص فقط.
2. تحديث قاعدة البيانات: تنفيذ migration التوافق بعد مراجعة المخطط الحالي.
3. إعداد الواجهة: ضبط الاتصال بـSupabase وتسجيل الدخول.
4. نشر الوظائف: نشر الوظائف المطلوبة وضبط الأسرار.
5. اختبار التحكم: readiness وstart وstop وقراءة حالة التشغيل.
6. اختبار البيانات: الأسواق والمنتجات والعملاء والطلبات.
7. اختبار Webhooks: استقبال أحداث تجريبية ومنع التكرار.
8. اختبار المهام: فحص الطابور وسجل التنفيذ.
9. التكاملات الخارجية: التحقق من Taager وEasyOrders كلٌ على حدة.
10. التقارير والأرباح: فصل الأرباح المتوقعة عن الأرباح المحققة.
11. اختبار الأمان: RLS والصلاحيات والأسرار وسجل التدقيق.
12. الإطلاق: بعد اجتياز جميع الاختبارات والموافقة على التشغيل.

5. التكاملات الخارجية

EasyOrders

يلزم التحقق من:

- API credentials.
- صلاحيات المنتجات والطلبات.
- صيغة Webhooks.
- طريقة التحقق من مصدر الطلب.
- حالات الطلب والتحديثات.
- إمكانية إرسال الطلبات واستقبالها.

Taager

يلزم التحقق من:

- إمكانات الربط المتاحة لحساب المستخدم.
- إمكانية الوصول إلى المنتجات وأكوادها.
- آلية متابعة الطلبات.
- حالات التسليم والتحصيل والمرتجعات.
- آلية معرفة الأرباح والسحب.

لا يتم افتراض وجود API أو مزامنة تلقائية دون إثبات رسمي.

Meta وWhatsApp

يلزم إعداد التطبيق والصلاحيات والقنوات وWebhooks وفق سياسات Meta.

الدفع والشحن

يتم تحديد كل بوابة وشركة شحن بحسب السوق، ثم اختبارها بشكل منفصل.

6. معادلة الأرباح

صافي الربح التقديري:

إجمالي المبيعات - تكلفة المنتج - الشحن - الإعلان - الخصومات - المصروفات الأخرى.

يجب التمييز بين:

- الربح المتوقع.
- الربح الناتج عن الطلبات المؤكدة.
- الربح المحقق بعد التسليم والتحصيل.
- صافي الربح بعد المرتجعات والمصروفات.

7. الأمان

- تفعيل ومراجعة RLS.
- التحقق من صلاحيات المستخدمين.
- حفظ الأسرار في الخادم فقط.
- عدم رفع مفاتيح الخدمة إلى GitHub.
- منع تكرار الطلبات والأحداث.
- تسجيل العمليات والأخطاء.
- عدم السماح بتشغيل الإعلانات أو الإنفاق دون موافقة.
